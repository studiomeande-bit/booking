# 내부 사고 기록 — 공개 슬롯 응답의 고객명·금액 노출

**작성 2026-09-21 · 상태: 내부 종결(감독청 통지 없음, 사장님 판단 2026-09-21)**
DSGVO Art. 33(4) 문서화 의무 이행용 내부 기록. 외부 제출용 아님.

## 1. 무슨 일이었나

예약 페이지의 **시간대 조회 API**(`api=slots`, 로그인 없이 호출 가능) 응답에 `anchorTitle` 이라는 필드가 있었고,
그 값이 **바로 옆 시간대 예약의 캘린더 일정 제목**이었다. 제목 형식은 시스템이 자동 생성하는
`상품명 | 고객명 | 인원 | 금액€` 이다(예: `스튜디오 Basic | 홍길동 | 2인 | 170€`).

- 노출 대상 데이터: **고객 이름, 예약 상품, 인원, 결제 금액**. (이메일·전화번호·주소는 이 응답에 없었다.)
- 대상 범위: 여권/프로필/스튜디오 촬영의 "추천 시간" 슬롯에 한함. 그 슬롯 옆에 실제 예약이 있을 때만 값이 채워졌다.
- 화면에는 표시되지 않았다. 브라우저가 받는 **데이터 안에만** 있었고, 사람이 보려면 개발자 도구나 직접 API 호출이 필요했다.

## 2. 기간

- **시작 2026-04-26** — 추천 시간 기능을 추가한 커밋 `6d73669`("Add recommended booking times and fast confirmation slots")에서 필드가 생겼다.
- **종료 2026-09-21** — 아래 조치로 값이 빈 문자열로 고정됐다.
- 약 5개월.

## 3. 어떻게 발견했나

2026-09-21 예약/셀렉 페이지 속도 개선 작업 중, 공개 라우트를 읽기 전용으로 점검하는 과정에서 발견했다.
고객 신고나 외부 제보가 아니다.

## 4. 조치 (당일 완료)

| 시각 | 내용 |
|---|---|
| 2026-09-21 | `buildPublicSlotEntries_` 가 `anchorTitle` 을 **항상 빈 값**으로 반환하도록 수정(응답 모양 호환을 위해 키만 유지) |
| 2026-09-21 | 슬롯 캐시 키를 `public_slots_v1_` → `v2_` 로 올려, 제목이 들어 있던 기존 캐시를 즉시 폐기 |
| 2026-09-21 | 메인 @978 · 셔틀 @16 배포 후, 양쪽 라이브에서 pass/prof/stud 세 그룹 모두 빈 값 확인. 다른 필드에 제목 형태 문자열이 남아 있지 않은지도 검사(없음) |

추천 라벨 표시에 실제로 필요한 값은 시간대(`anchorWindow`, 예: `11:00–11:15`)뿐이며, 프런트엔드와 예약 제출 경로 어디에서도 `anchorTitle` 을 읽지 않았다. 따라서 제거해도 기능 영향이 없다.

## 5. 위험 평가 (통지하지 않기로 한 근거)

- 화면에 노출되지 않았고, 값을 보려면 API 응답을 직접 열어 봐야 했다.
- 해당 필드를 읽어 간 흔적은 확인되지 않았다(프런트엔드에 참조 0건, 외부 문의·신고 없음).
- 노출 범위가 좁다: 추천 슬롯 옆에 예약이 있는 경우에 한해 이름·상품·인원·금액. 연락처·주소·결제수단은 포함되지 않았다.
- 대상자에게 **높은 위험**(Art. 34)을 초래할 성질로 보기 어렵다고 판단.
- **사장님 판단(2026-09-21): 정보 노출 가능성이 거의 없다고 보아 감독청 통지 없이 내부 종결. 본 기록으로 문서화 의무를 갈음한다.**

> 참고: 접근 로그가 없어 "읽힌 적 없다"를 적극적으로 증명하지는 못한다. 위 판단은 "악용 흔적이 확인되지 않음"에 근거한다.

## 6. 재발 방지 (적용 완료)

- 공개(무인증) 응답에 캘린더 일정의 제목·위치·설명을 싣지 않는다. 캘린더 제목은 그 자체가 개인정보다.
- 같은 날 공개 라우트 약 50개를 전수 감사했고(발견 29 · 확정 27), 확정 결함을 모두 수리·배포했다(메인 @980).
- 규칙을 프로젝트 메모리에 고정: `public-response-no-calendar-titles`, `gas-rpc-surface-and-admin-xss`.
- 공개 응답에 필드를 추가하거나 캘린더 상세 이벤트를 가공해 내보낼 때는 위 규칙을 먼저 점검한다.
