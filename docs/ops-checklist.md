## 1. 배포 절차

### 백엔드 (Apps Script)

```bash
cd appscript
clasp push                                   # HEAD 업로드 (이것만으론 웹앱 미반영!)
clasp deploy -i AKfycbxnHuB2u4-pDD23JDdFDpHB0ZIzGxLWm15Xgc7_-qkyOTctNpGlYDMIcQyq4KB7QC6X8w -d "설명"
```

- **이 배포 ID가 유일한 라이브** — 프론트·문서·이메일 링크 전부 이것만 참조. 절대 `clasp undeploy` 금지, 새 배포 생성 금지 (항상 `-i` 갱신).
- **버전 200개 한도**: deploy마다 버전이 쌓임. "Cannot create more versions" 에러 시 → Apps Script 편집기 → 프로젝트 기록에서 옛 버전 수동 삭제 (API 없음, 소유자만 가능).
- 로직만 바뀌면 push로 충분한 경우도 있지만, **HTML(AdminV2)·웹앱 동작 변경은 반드시 redeploy**.

### 프론트엔드 (Netlify)

```bash
cd frontend
npm run build:booking-site        # 또는 build:select-site / 개별 빌드
# index.html의 ?v= 캐시버스트 갱신 (필수!)
git add -A && git commit && git push origin main   # Netlify 자동 배포 (1~2분)
```

- min.js/min.css를 수정 후 **캐시버스트(?v=)를 안 올리면 CDN이 구버전 서빙** — 반드시 함께.
- booking과 select는 별도 Netlify 사이트 (booking.studio-mean.com / select.studio-mean.com).

### ERP 에이전트 (Claude)

- 키 파일: `reservation/.secrets/erp-automation-key` (gitignore) — 어드민 → 설정 → 자동화 API 키에서 발급/폐기.
- 스킬: `website/.claude/skills/studio-erp/SKILL.md` — 액션 목록·워크플로 문서.

## 2. Known Caveats

| 항목 | 내용 |
|---|---|
| GAS 버전 한도 | 200개 도달 시 배포 차단 — 정기적으로 프로젝트 기록에서 버전 정리 |
| **Utilities.formatDate 금지 (핫루프)** | GAS 서비스 호출이라 호출당 수십 ms — 시트 전 행을 도는 루프에 넣으면 수십 초가 된다 (2026-07-15 장부 107s→13s 사례). 분 단위 포맷은 `formatDateMinute_`(순수 JS, TZ 가드 내장) 사용. `getAccountingLedger` 응답의 `_timing`으로 페이즈별 진단 가능 |
| 캘린더 = 가용성 원본 | 캘린더에 이벤트를 넣으면 그 시간대 공개 슬롯이 막힘 (가예약 포함). 외부에서 직접 지운 이벤트는 시트와 어긋날 수 있음 |
| 셀렉 세션 중복 | 한 예약에 셀렉 세션이 2개 생길 수 있음 (재발송 이력) — 어드민 표시는 원본 세션 기준, 상태 변경은 `selectRowIndex` 지정 가능 |
| **납품 폴더 2GB 초과 = 분할 압축본 필수** | 🔴 Drive 일괄 다운로드는 2GB대에서 깨진다. 2026-08-17 실측으로 **평소 납품이 이미 600~800장 / 3.5~4.4GB**임을 확인했다(진희수 ~800장·4.4GB, 강예슬 ~650장·3.7GB, 이윤경 ~1,800장·7.9GB). 즉 **거의 모든 납품이 한계 초과**이고, 고객이 "전체 선택 → 다운로드"를 누르면 오류가 난다(이윤경 건 실제 클레임). 발송 시 어드민에 2GB 초과 안내가 뜨면 `scripts/split-delivery-zips.sh <원본> <대상>` 으로 **각각 독립적으로 열리는 zip 여러 개**(볼륨분할 `.zip.001` 아님 — 윈도우 탐색기가 못 연다)를 만들어 `<폴더명>_압축본` 폴더에 올리고 링크를 함께 안내할 것. 1200장/6GB 초과는 발송이 아예 막히며 `allowOversizedFolder:true` 로만 통과. 이미 나간 건 점검은 에이전트 액션 `select-folder-audit` |
| **인화 SKU 배포 전 필수** | `node scripts/check-print-prices.mjs` — 6개 정의처(가격 5곳 + 인보이스 라벨 2곳)를 자동 대조하고 구 등급명 잔존까지 잡는다. **불일치면 exit 1** → 고치기 전엔 배포하지 말 것. 가격·라벨·SKU를 건드렸으면 무조건 실행 |
| **프론트 배포 전 필수: 실제 로드 확인** | 🔴 `npm run build:*` 성공은 **동작 보증이 아니다**. esbuild 는 번들링만 하고 정의되지 않은 변수 참조 같은 런타임 오류를 잡지 못한다. 실제로 2026-07-27 셀렉 v2 가 `printTypeId is not defined` 로 페이지가 통째로 안 뜬 채 배포됐다(빌드·서버 API 검증은 전부 통과했다). 빌드·스탬프 후 **브라우저로 해당 페이지를 열어 콘솔 오류 0 + 본문 렌더까지 눈으로 확인**하고 푸시할 것 |
| **환불 규칙 배포 전 필수** | `node scripts/check-refund-rules.mjs` — 환불은 "상태가 아니라 결제 이벤트"다: 예약행 `환불내역JSON` 에 이벤트를 쌓고 가상 장부 빌더가 **지급일** 날짜의 음수 엔트리를 파생한다(원 매출행 불변 → 신고된 ELSTER 분기 소급 방지). `recordBookingRefund_`/`calcCancellationRefundQuote_` 원본을 떼어내 상한(누계≤실수령)·누적·forfeit·수단 폴백·규정 스케줄(일반 30/8/2일 · 웨딩 60/30/14/7일)을 검증. 결함 4종 주입 탐지 확인. 음수 엔트리는 매출 인식 상태(완료 3종/취소)에서만 나온다 |
| **환불 운용 규칙** | 부분환불 누적 가능(이벤트 append), 상한=실수령(초과 보상은 지출장부), 전체환불≠취소(상태 안 건드림), 취소 모달의 규정 제안액은 **제안일 뿐** 확정은 수동, 고객 메일·인보이스는 옵트인. 취소 시 환불 0€ 도 forfeit 이벤트로 기록돼 보유금(위약금)이 장부에 수입으로 잡힌다(이벤트 있는 취소건만 — 과거 취소건 소급 없음) |
| **환불 정책 (사장님 확정 2026-07-27)** | ① 취소 환불 규정 = **취소메일 규정으로 통일**(계약금 기준 30일+ 100% / 29~8일 50% / 7~2일 25% / 전일·당일 0%) — 예약 약관 텍스트도 동일하게 갱신됨. **웨딩은 별도**(60/30/14/7일, 100/70/50/30/0%). ② **여권 촬영미흡**으로 결과물을 못 쓰는 경우 실수령의 **50% 환불** — 환불 모달에 여권 건 전용 원클릭 프리셋(약관에는 미기재, 내부 운용 규칙). ③ **굿샤인 결제분 환불 = 바우처 복원**(현금 아님): 사용완료 → 메일발송/판매완료로 되돌리고 사용 이력 클리어, `gutschein_restore` 이벤트로 기록(현금 환불 누계·장부 음수 미포함). 이중 혜택 방지로 **취소된 예약 전용**. 원 판매 과세 유지라 Einzweck 부가세 문제가 안 생긴다 |
