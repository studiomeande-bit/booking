# 대표자 사적 인출이 비용으로 계상된 문제 (2026-08-05)

6~7월 은행 CSV 임포트 직후 지출 분류를 점검하다 발견. **두 개의 독립된 결함**이 겹쳐 있다.

## 결함 1 — 대표자 이체 제외 패턴이 풀네임만 잡음 (✅ 수정·배포 완료 @727)

`classifyBankOutExpense_` 의 제외 조건이 이랬다:

```js
if(/iban de98100110012627135089|taewoong min hyeda eun/i.test(counterparty+' '+description))
```

- 이름은 **풀네임 `taewoong min hyeda eun`** 만 매칭 → 은행 CSV 의 `Taewoong Min` 단독 이체는 통과
- IBAN 은 `iban ` **접두어가 붙은 형태**만 매칭 → 실제 tx 객체에는 IBAN 이 실리지 않음
  (`Verwendungszweck` 이 비면 `description` 은 **파일명으로 폴백**되고, IBAN 컬럼은 tx 에 담기지 않는다)

→ `Taewoong Min` 단독 이체 4건이 사적 인출(Privatentnahme)인데 **비용으로 계상**됐다.

| 날짜 | 금액 | 기존 패턴 |
|---|---|---|
| 2026-06-01 | €150 | ★누락 |
| 2026-06-11 | €400 | ★누락 |
| 2026-06-22 | €250 | ★누락 |
| 2026-07-27 | €200 | ★누락 |
| 2026-07-08 외 | €1,550 | 매칭됨(정상) |

**수정** (@727 배포):

```js
if(/de98100110012627135089|de62512500000000440760|taewoong\s*min|hyeda\s*eun/i
   .test(counterparty+' '+description+' '+String(tx&&tx.bankRef||'')))
```

- 이름 부분매칭(`taewoong\s*min`) + IBAN 을 접두어 없이 번호 자체로 매칭
- 검증 12/12 통과: 누락 4건 전부 제외 · 기존 매칭분 회귀 없음 · 임대료/아마존/우편/구독료 등 정상 비용 유지 · 고객 이름 오탐(`Min Jihoon`) 없음

## 결함 2 — dedup 신원키에 파일명이 섞여 중복 임포트 (✅ 수정 완료 @728)

`settlementIdentityKey_` 는 신원키에 `tx.description` 을 포함한다. 그런데 은행 tx 생성 시

```js
description: purpose || filename   // Verwendungszweck 이 비면 파일명으로 폴백
```

이라, **Verwendungszweck 이 빈 거래는 파일명이 신원키에 들어간다**. 같은 거래를 다른 파일로 재임포트하면 해시가 달라져 **중복 행이 생긴다**.

실제 발생 (6월, 대표자 이체 3건이 정확히 이 케이스 — 이체는 용도가 비어 있다):

| 날짜 | 금액 | 중복 |
|---|---|---|
| 2026-06-01 | €150 | `Kontoumsaetze_..._20260630_134835` + `Kontoumsaetze_20260803.csv` |
| 2026-06-11 | €400 | 〃 |
| 2026-06-22 | €250 | 〃 |

→ 6월 지출 **€800 과다**. (6/19 €4 x2 는 주차비·IONOS 로 **실제 별건**, 중복 아님.)

### 수정 내용 (@728)

신원키에서 **파일명형 설명만** 무력화하고, 기존 행을 놓치지 않도록 **신원키 인덱스를 폴백으로 추가**했다.

```js
function settlementDescriptionForKey_(desc){          // 신원 계산에서만 파일명 제거(표시값은 유지)
  const d=String(desc||'').trim();
  return (/\.csv$/i.test(d) || /^kontoums(ä|ae)tze/i.test(d)) ? '' : d;
}
```

- `getSettlementIndex_` 에 `byIdentity` 추가 — **시트 행 값에서 신원키를 재구성**하고, 같은 키가 여러 행이면
  시트 순서대로 `seq` 를 매겨 tx 쪽 seq 와 1:1 대응. 저장된 해시가 옛 산식(파일명 포함)이어도 행을 찾는다.
- `findSettlementRow_` 조회 순서: ref(SumUp) → 신규 해시 → legacy 해시 → **신원키 슬롯**
- 용도(Verwendungszweck)가 있는 거래는 정규화 대상이 아니라 **해시가 그대로** — 기존 매칭 경로 불변

### 검증

기존 행 매칭, **같은 날·같은 금액·같은 상대방의 별개 거래 2건은 서로 다른 행 유지**(뭉갬 없음), 신규 거래는 신규행.

### (참고) 수정이 위험했던 이유

신원키를 바꾸면 **기존 시트 행의 저장된 해시와 불일치**해, 다음 임포트가 전부 신규로 착각하고 대량 중복을 만든다. 코드 주석에도 같은 사고 이력이 남아 있다(`buildSettlementHashLegacy_` 는 그래서 조회 폴백으로 남겨둔 것).

**제안하는 방향** — 키 계산 시 파일명형 description 을 정규화해 무력화:

```js
function settlementDescriptionForKey_(desc){
  const d=String(desc||'');
  return (/^Kontoumsaetze/i.test(d) || /\.csv$/i.test(d)) ? '' : d;   // 파일명 폴백은 신원에서 제외
}
```

이러면 기존 행·신규 행 모두 키에서 파일명이 빠져 같은 해시로 수렴한다. 다만 **조회 폴백(구 해시)까지 함께 설계·검증**해야 하고, 검증에는 배포가 필요하다.

## 결함 3 — 독일식 천단위 구분자 파싱 오류 (✅ 수정 완료 @729)

`parseLocaleMoney_` 는 쉼표가 없고 **점만 있는** 값을 그대로 `Number()` 에 넘겼다. 독일 은행 CSV 는
소수점을 쉼표로 쓰므로 `1.428` 은 €1,428 인데 **1.43** 으로, `-1.000` 은 **-1** 로 읽혔다.

| 원본 | 잘못 읽힌 값 | 정답 | 건 |
|---|---|---|---|
| `1.428` | €1.43 | €1,428.00 | 7/8 KOREANISCHES GENERALKONSULAT (STMIN-260014 입금) |
| `-1.000` | €-1.00 | €-1,000.00 | 7/8 대표자 이체 |

영사관 인보이스 €1,428 입금이 €1.43 으로 들어가 **자동 매칭에 실패**하고 있었다.

**수정**: 점만 있을 때 — 점이 2개 이상이면 무조건 천단위, 1개면 뒤가 정확히 3자리일 때만 천단위로 본다.
영어권 `12.34`·`0.5` 는 소수점으로 유지. **검증 14/14**(독일식·영어권·회귀 전부).

## 결함 4 — SumUp CSV 이중 유입 (✅ 정리 + 파서 수정 @732)

**SumUp 은 이미 API 로 15분마다 자동 동기화된다**(`syncRecentSumupTransactionsTrigger`).
2026-08-05 에 `Verkaufsbericht` CSV 를 추가로 임포트하면서 같은 거래가 두 번 들어갔다.

게다가 파서가 이 CSV 의 컬럼을 못 읽고 있었다:

| 필요한 값 | CSV 컬럼 | 기존 후보 목록 | 결과 |
|---|---|---|---|
| 거래번호 | `Transaktionsnummer` | 없음 | **ref 공란 → SumUp 유일의 dedup 키가 무력화** |
| 결제수단 | `Zahlungsmethode` | 없음 | counterparty 가 `Verkauf`(=Typ 값) 로 들어감 |

→ ref 가 없으니 API 분과 대조되지 않아 33행 €2,802.00 이 통째로 중복됐다.

**정리**: `settlement-delete` 로 CSV 임포트분(ref 공란) 33행 삭제. API 분 32건 €2,802.00 이 정본
(합계 동일 — CSV 는 **아이템 단위**, API 는 **거래 단위**라 건수만 다르다.
예: 7/4 TAAA3ZGKQ7T 는 CSV 에서 €30+€45 두 줄, API 에서 €75 한 건).

**파서 수정**: ref 후보에 `Transaktionsnummer`·`Beleg-Nr`, type 에 `Typ`, counterparty 에 `Zahlungsmethode` 추가.
이제 CSV 를 다시 넣어도 ref 로 dedup 된다. 다만 **SumUp CSV 임포트는 원칙적으로 불필요** —
API 공백 기간을 메울 때만 쓸 것(코드 주석에도 명시).
